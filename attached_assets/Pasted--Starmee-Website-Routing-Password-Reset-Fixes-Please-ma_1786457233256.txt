Please make the following changes to the Starmee website/application. Before making changes, inspect the existing codebase and determine how routing, authentication, the Starmee logo/header, user accounts, and password storage/reset functionality are currently implemented. Preserve all existing functionality and styling unless specifically instructed below.

`https://starmeestories.com/`

### Important implementation requirements

* Update the logo's link/navigation behavior so its destination is exactly:
  `https://starmeestories.com/`

  * Logged out
  * Logged in
  * On `/create`

  * On another authenticated application page

* Do not change the behavior of other navigation links.
* If the application currently uses React Router, Next.js routing, or another client-side router, determine whether an external absolute URL is required and implement it appropriately.
* Do not create a redirect loop between `starmeestories.com` and `app.starmeestories.com`.

# 2. Add Secure "Forgot Password" / Password Reset Functionality

Add a complete, production-ready password reset workflow to:

`https://app.starmeestories.com/auth/login`

The goal is to allow a user who has forgotten their password to securely reset it without requiring administrator intervention.

## Login page

Add a clearly visible:

**Forgot Password?**

link near the existing password field/login controls.

Clicking it should take the user to a dedicated password recovery page, for example:

`/auth/forgot-password`

Use the application's existing routing conventions if a different structure is already established.

---

## Forgot Password Page

Create a page where the user can enter the email address associated with their Starmee account.

Example:

**Forgot your password?**

Enter your email address and we'll send you a secure link to reset your password.

[ Email Address ]

[ Send Reset Link ]

[ Back to Login ]

### Security requirements

The implementation must NOT reveal whether an email address exists in the database.

For example, after submitting the form, show the same generic message whether the account exists or does not exist:

**If an account exists for that email address, we've sent you a password reset link. Please check your inbox.**

Do not display messages such as:

* "Email not found"
* "No account exists"
* "That email isn't registered"

This prevents account enumeration.

# Password Reset Token

Use a secure, cryptographically random, single-use password reset token.

Do NOT use:

* The user's ID
* The user's email address
* A timestamp
* A predictable token
* The existing password
* Any other predictable value

The reset token should have a limited expiration period. A reasonable default is **1 hour**.

Prefer storing a secure hash of the reset token in the database rather than storing the raw token.

The database record should contain enough information to:

* Identify the user
* Validate the token
* Determine when it expires
* Determine whether it has already been used
* Invalidate the token after successful use

For example, conceptually:

`user_id`
`token_hash`
`expires_at`
`used_at`
`created_at`

Adapt this to the application's existing database/schema conventions rather than blindly creating a new architecture.

---

# Reset Password Link

The email should contain a secure link similar to:

`https://app.starmeestories.com/auth/reset-password?token=SECURE_TOKEN`

Do not put sensitive information other than the reset token into the URL.

The token should:

* Be sufficiently long and cryptographically random
* Be single-use
* Expire after the configured period
* Become invalid immediately after successful password reset
* Be invalid if already used
* Not expose the user's current password

# Successful Password Reset

After a successful password reset:

1. Invalidate the reset token immediately.
2. Update the user's password using the application's existing secure password-hashing mechanism.
3. Prevent the same reset link from being used again.
4. Redirect the user to the login page or an appropriate authenticated destination.
5. Display a confirmation such as:

**Your password has been reset successfully. You can now log in with your new password.**

Do not automatically expose sensitive account information.

---

* Already used

**This password reset link is invalid or has expired. Please request a new password reset link.**

Provide a button/link to:

**Request a New Reset Link**

Do not expose database errors, stack traces, token values, or other implementation details.

# Additional Security Requirements

Please implement the password-reset workflow using standard secure authentication practices.

Specifically:

### Rate limiting

Protect the forgot-password endpoint against abuse.

A user/IP should not be able to repeatedly request unlimited reset emails.

Use the application's existing rate-limiting infrastructure if available. If none exists, implement a reasonable server-side limit.

### No account enumeration

The forgot-password response must be identical whether or not the email exists.

### Token security

Use a cryptographically secure random token.

Store only a secure hash of the token where practical.

Make tokens single-use and time-limited.

### Password security

Never:

* Store plaintext passwords
* Log plaintext passwords
* Send passwords through email
* Include passwords in URLs
* Return passwords through API responses

Use the application's existing secure password hashing implementation.

### Session security

Inspect how authentication sessions are currently implemented.

After a password reset, determine whether existing sessions should be invalidated. If the current authentication architecture supports session revocation, invalidate existing sessions after a successful password change so that a compromised account cannot remain authenticated on another device.

Do not introduce a conflicting authentication/session system.

### CSRF / request security

Follow the application's existing CSRF and API security patterns. Do not create a less-secure exception specifically for password reset.

### Frontend/backend separation

Password reset validation and token verification must happen server-side.

Do not put password-reset secrets, database credentials, email API keys, or other sensitive credentials into frontend/client-side code.
